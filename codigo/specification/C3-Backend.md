## Implementation Guidelines for Backend Developers

This document provides detailed guidelines for developers working on the AI-Enhanced Personal Finance Management System backend. It outlines the architecture, component structure, conventions, and implementation rules to ensure architectural consistency.

## 1. Project Structure and Organization

The backend system follows a microservices architecture, with each service focused on a specific business domain. Each microservice has a similar internal structure following layered architecture principles.

### 1.1 Project Structure

Each microservice follows a standardized project structure:

```
service-name/
├── src/
│   ├── main/
│   │   ├── java/com/pfm/servicename/
│   │   │   ├── config/           # Configuration classes
│   │   │   ├── controller/       # REST API controllers
│   │   │   ├── dto/              # Data Transfer Objects
│   │   │   ├── exception/        # Custom exceptions
│   │   │   ├── mapper/           # DTO-Entity mappers
│   │   │   ├── model/            # Domain entities
│   │   │   ├── repository/       # Data access layer
│   │   │   ├── security/         # Security-related classes
│   │   │   ├── service/          # Business logic
│   │   │   └── util/             # Utility classes
│   │   └── resources/
│   │       ├── application.yml   # Application configuration
│   │       ├── bootstrap.yml     # Bootstrap configuration
│   │       └── db/migration/     # Database migrations
│   └── test/                     # Test classes mirroring main structure
```

## 2. Layer Architecture and Communication

### 2.1 Layered Architecture

Each microservice follows a layered architecture with clear separation of concerns:

1. **Controller Layer**
   - Handles HTTP requests/responses
   - Input validation
   - Authentication/authorization checks
   - Maps request data to DTOs
   - Delegates business processing to Service layer

2. **Service Layer**
   - Contains business logic
   - Orchestrates business workflows
   - Manages transactions
   - Maps between DTOs and domain entities
   - Handles business exceptions

3. **Repository Layer**
   - Provides data access abstraction
   - Handles database operations
   - Maps between entities and database tables

4. **Domain Model Layer**
   - Contains domain entities
   - Encapsulates business rules
   - Represents core business concepts

### 2.2 Layer Communication Rules

Follow these rules for communication between layers:

1. **Direction of Dependency**:
   - Upper layers can depend on lower layers, not vice versa
   - Controllers → Services → Repositories → Entities

2. **Layer Crossing**:
   - Controllers should only call Services, never Repositories directly
   - Services can call other Services and Repositories
   - Repositories should not call Services

3. **Data Transfer**:
   - Controllers receive and return DTOs, never entities
   - Services translate between DTOs and entities
   - Repositories work with entities, never DTOs

4. **External Communication**:
   - Service-to-service communication happens only at the Service layer
   - Use dedicated client classes for external API calls

## 3. Naming Conventions

### 3.1 Java Class Naming

| Component Type | Convention | Example |
|----------------|------------|---------|
| Controller | `{Entity}Controller` | `UserController` |
| Service Interface | `{Entity}Service` | `UserService` |
| Service Implementation | `{Entity}ServiceImpl` | `UserServiceImpl` |
| Repository Interface | `{Entity}Repository` | `UserRepository` |
| Entity | Simple noun | `User`, `Transaction` |
| DTO | `{Entity}{Purpose}Dto` | `UserCreationDto`, `UserResponseDto` |
| Exception | `{Descriptive}Exception` | `UserNotFoundException` |
| Configuration | `{Feature}Config` | `SecurityConfig` |
| Mapper | `{Entity}Mapper` | `UserMapper` |

### 3.2 REST API Endpoint Naming

- Use plural nouns for resources: `/users`, `/transactions`
- Use sub-resources for relationships: `/users/{id}/accounts`
- Use verbs for operations that don't fit CRUD: `/transactions/{id}/categorize`
- Include API version in URL path: `/api/v1/users`
- Use kebab-case for multi-word resources: `/budget-categories`

### 3.3 Database Naming

- Table names: Plural, snake_case: `users`, `financial_accounts`
- Column names: Snake_case: `first_name`, `account_number`
- Primary keys: `id` or `{table_name}_id` for composite tables
- Foreign keys: `{referenced_table_singular}_id`
- Junction tables: `{table1}_{table2}`: `users_roles`
- Indices: `idx_{table}_{column(s)}`

### 5.2 Asynchronous Communication

For asynchronous communication, use Kafka:

```java
@Service
public class TransactionServiceImpl implements TransactionService {
    
    private final KafkaTemplate<String, TransactionEvent> kafkaTemplate;
    
    // Constructor injection
    
    @Override
    public TransactionResponseDto createTransaction(TransactionCreationDto dto) {
        // Save transaction
        Transaction transaction = transactionMapper.toEntity(dto);
        transaction = transactionRepository.save(transaction);
        
        // Publish event for other services
        TransactionEvent event = new TransactionEvent(
            transaction.getId(),
            transaction.getAmount(),
            transaction.getCategory(),
            transaction.getTimestamp()
        );
        
        kafkaTemplate.send("transactions.created", event);
        
        return transactionMapper.toDto(transaction);
    }
}
```

## 7. Testing Standards

### 7.1 Unit Testing

Use JUnit 5 and Mockito for unit tests:

```java
@ExtendWith(MockitoExtension.class)

    }
}
```

```java
@Service
public class TransactionServiceImpl implements TransactionService {
    
    private final TransactionRepository transactionRepository;
    private final CategoryRepository categoryRepository;
    private final TransactionMapper transactionMapper;
    private final KafkaTemplate<String, TransactionEvent> kafkaTemplate;
    
    // Constructor injection
    
    @Override
    @Transactional
    public TransactionCategorizationResponse categorizeTransaction(Long id, TransactionCategorizationRequest request) {
        Transaction transaction = transactionRepository.findById(id)
            .orElseThrow(() -> new TransactionNotFoundException("Transaction not found with id: " + id));
        
        Category category;
        boolean isCustomCategory = false;
        
        if (request.getCategoryId() != null) {
            category = categoryRepository.findById(request.getCategoryId())
                .orElseThrow(() -> new CategoryNotFoundException("Category not found with id: " + request.getCategoryId()));
        } else if (StringUtils.hasText(request.getCustomCategoryName())) {
            category = new Category();
            category.setName(request.getCustomCategoryName());
            category.setCustom(true);
            category = categoryRepository.save(category);
            isCustomCategory = true;
        } else {
            throw new BusinessException("Either category ID or custom category name must be provided");
        }
        
        transaction.setCategory(category);
        transaction.setCategorizedAt(LocalDateTime.now());
        transaction = transactionRepository.save(transaction);
        
        // Publish event
        TransactionEvent event = new TransactionEvent();
        event.setTransactionId(transaction.getId());
        event.setEventType(TransactionEventType.CATEGORIZED);
        event.setCategoryId(category.getId());
        kafkaTemplate.send("transactions.categorized", event);
        
        TransactionCategorizationResponse response = new TransactionCategorizationResponse();
        response.setTransactionId(transaction.getId());
        response.setCategoryName(category.getName());
        response.setCustomCategory(isCustomCategory);
        response.setCategorizedAt(transaction.getCategorizedAt());
        
        return response;
    }
}
```

## 11. Architectural Constraints

### 11.1 Dependency Constraints

- Services must not have circular dependencies
- Dependencies must be explicitly declared in the service's build file (pom.xml)
- Use dependency injection through constructors, not field injection
- Keep external library dependencies to a minimum to reduce vulnerability surface

### 11.2 API Constraints

- All endpoints must be versioned
- All endpoints must have proper documentation
- Use DTOs for all external communication, never entities
- REST resources should follow REST principles
- Return appropriate HTTP status codes

### 11.3 Data Storage Constraints

- No direct database access from the services to other services' databases
- Each service owns its data exclusively
- Use database migrations for all schema changes
- Validate data integrity at the application level, not just database level

### 11.4 Security Constraints

- No sensitive data in logs
- No sensitive data in URLs
- Use parameterized queries to prevent SQL injection
- Use proper input sanitization and validation
- Encrypt sensitive data at rest
- Use TLS for all communications
